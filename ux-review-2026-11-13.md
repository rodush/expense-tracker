# UI and UX review — 2026-11-13

## Scope

Heuristic review of the current Svelte interface and its import, filtering, overview, transaction and export flows, informed by the product workflow and CSS. This is a source review, not a live usability test or an accessibility audit; visual behavior, assistive technology and real user outcomes still need validation in a running app. The checked-in screenshots appear to depict an earlier interface and were not treated as evidence of the current layout.

## Prioritized findings

### High — Sorting implies a whole-ledger order but only sorts one page

The transaction headers offer sorting without qualification, but `PreviewPanel.svelte` sorts only the 25 rows already returned. Moving to another page can therefore reveal a larger amount after a smaller one, or an earlier date after a later one. This undermines comparisons and makes finding a transaction unreliable. The active sort direction is also communicated visually, without `aria-sort` on the header.

**Recommendation:** Sort the filtered dataset on the server before pagination, retain the chosen sort across pages, and expose direction using `aria-sort`. Until that is available, clearly label sorting as applying to the current page. Validate with more than 25 records and keyboard/screen-reader testing.

### High — A failed refresh can leave old figures beside new filters

`loadHistory` retains the prior rows and summary on failure. The selected controls and export link already reflect the new filters, so the displayed totals and rows can describe a different selection from the export. Filter options also load independently and their error can be cleared by the history request.

**Recommendation:** Make the displayed data's filter state explicit; on failure either clear or clearly mark previous results as stale, disable export for an unconfirmed selection, and provide a retry. Keep filter-option errors separate. Test failed and out-of-order requests.

### High — Amounts lack currency context

Totals and transaction amounts are formatted as numbers with two decimals but no currency. The architecture decision records a single EUR assumption; users cannot see that assumption when interpreting or exporting a report.

**Recommendation:** Label monetary values as EUR consistently, including the total, tables and chart, and state the single-currency assumption during import. Do not imply conversion or mixed-currency support.

### Medium — First import is hard to discover and prepare

The upload control starts collapsed even for an empty ledger. The empty history says no expenses match filters, which does not distinguish an empty ledger from a filtered-out result. The file picker lists extensions and size but omits required date, amount and description columns and supported bank headers. Users may discover requirements only after a failed upload.

**Recommendation:** Open or prominently present import for a genuinely empty ledger; explain required columns and link to a sample or format guidance. Give first-use and no-filter-results states distinct messages and actions. Preserve a compact import control for returning users.

### Medium — Import outcome and data handling need clearer expectations

“Analyze expenses” does not explain that importing persists transactions, resolves people, categorizes new records and skips duplicates. The generic statement that the file prepares a report does not explain storage or processing, which matters for bank data. Success reports counts but does not guide review of classifications, and the accordion closes immediately.

**Recommendation:** Explain the actual processing and persistence in concise, accurate language before submission, including any external processing where applicable. After import, keep the count confirmation prominent and offer a clear path to inspect newly imported or potentially uncertain classifications, subject to available API capabilities.

### Medium — Date controls silently replace each other

Changing the range clears the quick year/month; changing the quick selection clears the range. This is not explained near the controls. A reversed range also has no inline guidance, and date inputs trigger requests on each input event.

**Recommendation:** Present these as mutually exclusive modes or explain the replacement before it happens. Validate the range inline, preserve understandable feedback, and avoid unnecessary intermediate requests. Test keyboard entry and switching modes.

### Medium — Small-screen transaction discovery and keyboard effort

The five-column transaction table uses horizontal scrolling and truncated descriptions with a tooltip. The scroll area gives no explicit cue that more columns exist, while each description is a separate tab stop. On touch, the hover/focus tooltip is not an obvious way to reveal full text.

**Recommendation:** Test at narrow widths with touch and keyboard. Provide a visible scroll cue or a compact expandable transaction layout, and make full descriptions available through an explicit accessible interaction. Avoid requiring a tab stop for every static cell.

### Medium — Loading and empty states obscure the report's status

Only the transaction list explicitly shows loading; the previous summary remains visible while filters update. When the summary count is zero, empty messaging appears alongside the report grid and a second empty message in the transactions section. This can make an empty or updating report look complete.

**Recommendation:** Show a coherent loading state for the whole report, distinguish no data from no matching results, and replace empty charts/tables with one actionable explanation. Ensure status updates are announced without excessive repetition.

### Low — Overview hierarchy and chart accessibility

The total spend appears after category and person breakdowns in the document order, although it is the natural starting point for interpreting the report. The chart has a generic accessible label; its equivalent category table is inside a closed disclosure. Sorting controls in summary tables likewise lack programmatic sort state.

**Recommendation:** Lead with total and the active period/filter context, then breakdowns. Provide a readily discoverable text equivalent for the chart and expose sort direction on table headers. Verify chart colors and contrast in the running interface.

## What works

The interface uses labeled native file, date, checkbox and select controls; grouping with fieldsets makes filters easier to understand. It reports duplicate counts after import, provides a clear-filter action, shows the active filter summary, and offers a filtered CSV export. Pagination includes a visible range and disabled boundary buttons.

## Suggested validation

First address global sorting and stale results, then test the first-import and no-results journeys with representative data. Run a keyboard and screen-reader pass, inspect desktop and narrow mobile layouts, and observe users completing import, finding a transaction across pages, applying a date filter and exporting the result. Confirm currency and processing language against the deployed configuration before presenting it to users.
