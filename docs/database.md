# Database operations

The application uses SQLAlchemy 2.x for relational data access and Alembic for
versioned schema migrations. Local development defaults to SQLite at
`./expense-tracker.db` (relative to the process working directory). Set
`DATABASE_URL` to a SQLAlchemy connection URL to select another supported
relational database. Keep database URLs and credentials in environment
variables or the deployment platform's secret store; never commit credentials
to `.env`, source, or container images.

The upload and history APIs use the configured database for import batches and
canonical expense records. An import batch describes an uploaded statement;
its newly recognized rows become durable ledger entries. Expense records are
queried across all batches and do not expire. Dataset ownership is nullable in
preparation for authentication in Milestone 5. Category and `who` rules are
deployment-level configuration in this milestone; the schema reserves rule-set
tables for later account-scoped configuration. App instances using the same
database share the same expense history.

Exact file re-uploads are short-circuited by a persisted SHA-256 file hash.
Overlapping exports are deduplicated by a key built from normalized bank
fields, with an occurrence number preserving identical rows inside one import.
Because the current export contract provides no stable bank transaction ID,
two truly identical purchases cannot always be distinguished across different
files. If the bank supplies a stable reference, use it as the record key in a
future schema revision.

## Local development

From the repository root, install the locked Python dependencies and apply the
schema:

```sh
uv sync
uv run alembic upgrade head
```

With no `DATABASE_URL`, the database is created at `expense-tracker.db` in the
working directory. To choose another local path, set an absolute SQLite URL,
for example:

```sh
export DATABASE_URL='sqlite:////home/me/data/expense-tracker.db'
uv run alembic upgrade head
```

Useful inspection commands:

```sh
uv run alembic current
uv run alembic history
```

When changing ORM models, generate a candidate migration, review it, then
apply it:

```sh
uv run alembic revision --autogenerate -m "describe schema change"
uv run alembic upgrade head
```

Autogenerated migrations are drafts: inspect the operations and any data
transformation before committing. Do not use `Base.metadata.create_all()` as
an application startup migration mechanism. Alembic revisions are the schema
source of truth, and should be applied as a deployment step before serving
traffic with code that expects the new schema.

## Production configuration and deployment

Configure `DATABASE_URL` through the hosting platform's secret/configuration
mechanism. A PostgreSQL URL commonly has this shape:

```text
postgresql+psycopg://USER:PASSWORD@DB_HOST:5432/DATABASE_NAME
```

Use a database account with only the privileges the application needs, require
TLS when the database is remote, and URL-encode reserved characters in URL
credentials. Do not print the URL in logs or expose it through health
endpoints. The selected driver must be installed in the project environment.

For production, PostgreSQL is supported through the locked Psycopg 3 binary
driver; use a managed database service with durable storage, monitoring, and
tested backups. SQLite is suitable for local development and small single-host
deployments with a persistent local disk. It is not a shared database across
multiple hosts; avoid placing its file on network filesystems or starting
multiple application hosts against a shared SQLite file. Ensure the database
location is on persistent storage and writable by the service account. Treat
container-local storage as ephemeral unless the deployment explicitly mounts
a durable volume.

Run `uv run alembic upgrade head` once as a release/deployment job using the
same configuration and database credentials as the application. For a
multi-instance deployment, coordinate migrations so only one release job
updates the schema at a time. Back up the database before migrations that may
drop, rewrite, or transform data, and use an expand/migrate/contract sequence
when old and new application instances might overlap during a rollout.

## Backup and restore

Backups contain sensitive financial data. Restrict access, encrypt backup
files and transfer channels, set a defined retention period, and verify
restores regularly in an isolated environment. A successful backup command
alone does not establish that recovery works.

For a quiesced SQLite database, use SQLite's online backup command rather than
copying a live database file:

```sh
sqlite3 expense-tracker.db ".backup 'expense-tracker-backup.db'"
```

For automated backups, use the SQLite backup API or stop writes while making
the backup. If SQLite write-ahead logging (WAL) is enabled, do not copy only
the main `.db` file while the database is active; use the online backup API or
checkpoint and stop the application first. Restore by stopping the app,
preserving the existing database for investigation, placing the verified
backup at the configured database path, and then starting the app. Confirm
the expected Alembic revision with `uv run alembic current`.

For PostgreSQL, use the provider's managed backup/PITR facilities or
`pg_dump`/`pg_restore` according to the deployment's recovery objectives.
Back up before schema changes; after restore, verify connectivity, migration
revision, and a representative read before routing traffic. Keep recovery
credentials separate from normal application credentials.

## Expense retention and generated downloads

Expense history is persistent and has no expiration field or cleanup job.
There is no user-visible deletion API in this milestone. Treat financial
records as retained indefinitely; any manual removal should be a controlled
database maintenance action that also removes associated import metadata.
Database backups can retain deleted records until those backups expire; include
this in any deletion policy.

Per-import categorized CSV downloads can be regenerated from persisted rows
after a restart or local file loss. Generated files are stored under the
configured downloads directory (by default `.tmp` under the process working directory).
The current implementation does not provide a generated-file expiration or
cleanup job. For deployments, place this directory on appropriately protected
storage, account for it in disk monitoring and backup/deletion procedures, and
remove stale exports with controlled operational cleanup. Do not assume
deleting an import batch also deletes an already generated CSV. Future automated
retention must define dataset and export lifetimes together, remove exports
safely, and avoid deleting files that are still being served.

These limits must be revisited before public production use: define a user
visible retention policy, authenticated expense deletion, an auditable cleanup
job, and export expiry/cleanup behavior before treating persisted financial
data as production-ready.
